# Pipeline: Article Production

*End-to-end pipeline for researching, writing, and expert-reviewing COSMOS encyclopedia articles. Defines phases, agent assembly, model tiers, handoff protocol, and verification gates.*

---

## Overview

```
Phase 1: RESEARCH → Spec (facts, images, sources — complete enough to write from)
Phase 1b: SPEC REVIEW → Completeness gate (can the writer produce an article without guessing?)
Phase 2: WRITE (article) → VERIFY (voice, grammar, accuracy) → pass
Phase 3: EXPERT REVIEW → crowdsourced vetting by department astronomers
Phase 4: DONE — update tracking, cross-link, commit
```

## Agent Assembly (Role + Domain → Agent)

**How the orchestrator dispatches agents:**

The orchestrator does NOT read role or domain files itself. It sends a short prompt with:
1. Which files the agent must read (role + domain)
2. The task context (topic, slug, paths)

The agent reads its own files and knows how to do its job. This keeps the orchestrator lightweight and ensures domain knowledge is always read from the source of truth, never summarised or paraphrased.

| Phase | Files agent must read (in order) | Model | Task context |
|-------|----------------------------------|-------|-------------|
| 1 | `roles/researcher.md`, `domains/cosmos-article-research.md` | **opus** | topic, category, seed URL, output path |
| 1b (optional) | `roles/verifier.md`, `domains/cosmos-article-research.md` | **sonnet** | spec path |
| 2 (write) | `roles/writer.md`, `COSMOS-STYLE-GUIDE.md`, `domains/cosmos-articles.md` | **sonnet** | spec path, article path |
| 2 (verify) | `roles/verifier.md`, `domains/cosmos-articles.md` | **opus** | article path, spec path |
| 3 | External (Google Forms + expert reviewers) | N/A | N/A |

### Standard dispatch prompt template

The orchestrator prompt for ANY agent in this pipeline follows this pattern:

```
You are a COSMOS encyclopedia {role}.

Read these files before doing anything else:
1. .agents/roles/{role}.md
2. .agents/domains/{domain}.md
[3. .agents/COSMOS-STYLE-GUIDE.md — for writer/article-verifier only]

Then execute the task:
  Topic: {keyword}
  Slug: {slug}
  Category: {category}
  [Seed URL: {url} — researcher only, if available]
  Spec path: .planning/content/specs/{slug}/{slug}-spec.md
  Article path: articles/{slug}.html
  [Image path: images/{slug}-{desc}.jpg — writer only, after copy-recommended-image.js]
```

**Do NOT add anything else to the prompt.** No summaries of voice rules, no inline style guidance, no examples. The files contain everything. Adding orchestrator commentary risks contradicting or diluting the domain files.

## Tracking

**Single source of truth:** `.planning/content/pipeline-status.md`

Generated by `dev/init-pipeline-status.js` from the master article list. Updated by each agent after completing its phase.

```markdown
| slug | title | tier | phase-1-research | phase-2-writing | phase-3-review | notes |
|------|-------|------|------------------|-----------------|----------------|-------|
```

**Statuses:** `-` (not started), `in-progress`, `done`, `queued` (Phase 3: staged for review), `revision`, `approved`, `skipped`.

## Phase Details

### Phase 1: Research

**Dispatch:** Researcher with `cosmos-article-research` domain.

**Dispatch using the standard prompt template above.** The researcher reads its own domain file which contains milestones, source hierarchy, image rules, spec template, and mandatory post-completion scripts.

**Output:** `.planning/content/specs/{slug}/` directory containing:
- `{slug}-spec.md` — structured spec with all factual content
- Downloaded images (`.jpg`/`.png`)
- `{image-name}-caption.md` — caption + original source reference per image

**Spec completeness rule:** The spec must contain ALL factual content the writer needs. The writer's job is voice/style/structure only — they must never research, extrapolate, or guess. If the spec is too thin for a 200–400 word article, the researcher must deepen it before handing off.

**Handoff:** Researcher includes `## Handoff: Researcher → Writer` at end of spec.

**After completion:**
```bash
node dev/update-pipeline-status.js {slug} phase-1-research done
```

### Phase 1b: Spec Review (mechanical + optional agent)

**Always run the mechanical preflight (zero tokens):**
```bash
node dev/check-spec.js {slug}
```
If it fails, fix issues and re-run until it passes. This catches: missing STATUS, missing sections, invalid images, missing captions.

**Agent review is optional.** If `check-spec.js` passes, the spec is structurally complete. Dispatch a verifier agent (sonnet) only if:
- The topic is complex or contentious (e.g. dark energy, alternative cosmologies)
- The researcher flagged gaps in the handoff
- You want extra confidence before spending tokens on writing

If dispatched, the verifier judges content sufficiency — not mechanical completeness (the script handles that).

**If FAIL:** Return spec to researcher with specific gaps. Re-check (max 2 rounds).
**If PASS (or skipped):** Move to Phase 2.

### Phase 2: Write + Verify

**Dispatch writer** with `cosmos-articles` domain.

**Before dispatching the writer, run these pre-write scripts:**
```bash
# 1. Scaffold the article HTML + update indexes
node dev/new-article.js "{Title}"

# 2. Copy recommended image from spec dir to images/ — prints the dest path
node dev/copy-recommended-image.js {slug}
#    → outputs e.g. images/solar-system-montage.jpg
```

**Dispatch using the standard prompt template above.** One fresh agent per article — never batch. Include the image path from step 2 in the task context. The writer reads its own domain files which contain voice rules, image placement, length guidelines, and mandatory post-completion scripts.

**After writer completes, run these post-write scripts (no tokens):**
```bash
# 1. Cross-link: match terms against article index, wrap in lexicon-term anchors
node dev/cross-link-articles.js articles/{slug}.html

# 2. Mechanical preflight — catches contractions, "data is", missing image, etc.
node dev/check-article.js articles/{slug}.html

# 3. Update tracking
node dev/update-pipeline-status.js {slug} phase-2-writing done
```

Only dispatch the verifier agent if `check-article.js` passes. The agent judges voice quality and factual accuracy — not mechanical errors the scripts already catch.

**Then dispatch verifier** with `cosmos-articles` domain.

**Verifier focus (mechanical checks already handled by `check-article.js`):**
| # | Check | Reject if |
|---|-------|-----------|
| 1 | Opens with direct definition | Preamble or conversational hook |
| 2 | Semi-formal register, correct voice | Conversational tone, editorialising |
| 3 | No editorial fluff or AI slop | Dramatic qualifiers, rhetorical questions, superlatives, emotional amplification |
| 4 | Length appropriate to topic | Simple definition padded, or rich topic compressed |
| 5 | All facts traceable to spec | Writer invented or extrapolated content |
| 6 | Australian/British spelling | American spelling (color, ionization) |

**Routing:**
- PASS → Phase 3
- FAIL → feedback to writer, re-dispatch (max 3)

**After completion:**
```bash
node dev/update-pipeline-status.js {slug} phase-3-review approved
```

### Phase 3: Expert Review

**External process** — not an agent phase. Managed via Google Sheets + Apps Script web app + review UI.

**Branch strategy:** All development happens on `dev-agent`. GitHub Actions deploys `dev-agent` as the site; `main` branch articles are copied to `/stable/articles/` as the blessed snapshot. Articles are merged to `main` after approval.

**Infrastructure:**
- Review UI: `review/index.html` + `review/app.js` (reads assignments from Apps Script)
- Apps Script: `dev/review/apps-script.js` (deployed as web app on Google Sheets)
- Config: `dev/review/config.json` (contains the Apps Script deployment URL)

**Staging articles for review:**
```bash
# 1. Commit + push articles on dev-agent
git add articles/{slug1}.html articles/{slug2}.html images/...
git commit -m "Add articles: slug1, slug2, ..."
git push origin dev-agent

# 2. Stage for review (updates tracking, creates assignments, sends email)
node dev/stage-for-review.js --reviewer="Name <email>" slug1 slug2 slug3
```

**Review workflow:**
1. Reviewer receives email with link: `https://ivolabbe.github.io/cosmos/review/?reviewer=email`
2. Review page fetches assignments from Google Sheet via Apps Script
3. First pending article loads in iframe; reviewer clicks Approve / Correction / Skip
4. Corrections require a text description; responses recorded in Google Sheet
5. Reviewer can stop at any time; revisiting the URL resumes from the first pending article

**Syncing results back:**
```bash
# Pull review verdicts from Google Sheet into pipeline-status.md
node dev/sync-review-status.js
```

**Routing:**
- `approved` → Phase 4 (merge to main)
- `revision` → feedback from Google Sheet; article returns to Phase 2 for corrections
- `skipped` → reassign to another reviewer or re-stage

**Resetting (for test re-runs):**
```bash
node dev/reset-review.js slug1 slug2    # resets pipeline-status.md + Google Sheet
```

### Phase 4: Done

Cross-linking and status updates already happened per-article in Phase 2. This phase is batch-level cleanup:

1. **Verify tracking:** Confirm all articles in the batch show `done | done | approved` in `pipeline-status.md`
2. **Merge to main:**
   ```bash
   git checkout main
   git checkout dev-agent -- articles/{slug1}.html articles/{slug2}.html images/...
   git commit -m "Publish approved articles: slug1, slug2, ..."
   git push origin main
   git checkout dev-agent
   ```
3. **Verify blessed snapshot:** Check `https://ivolabbe.github.io/cosmos/stable/articles/{slug}.html`

## Batch Execution

Research specs can run in parallel (no inter-article dependencies). Process in priority order:

| Tier | Score (imp × pop) | ~Count | Priority |
|------|-------------------|--------|----------|
| 1 | ≥ 72 | ~200 | First |
| 2 | ≥ 42 | ~400 | Second |
| 3 | < 42 | ~800 | Third |

Within each tier, dispatch up to 4 concurrent research agents. Writing depends on research completion per article, but articles are independent of each other.

**Skip existing articles.** Any article with a non-empty `notes: existing: {slug}` in `pipeline-status.md` already has content in `articles/` or `articles_orig/`. Do not research, write, or overwrite these. They will be handled separately in the maintenance pipeline.

## Verification Gate Summary

| Gate | When | What it checks | Blocks |
|------|------|----------------|--------|
| **Spec review** (Phase 1b) | After research | Spec completeness for writing | Phase 2 |
| **Article verify** (Phase 2) | After writer | Voice, grammar, accuracy, no invented content | Phase 3 |
| **Expert review** (Phase 3) | After article verify | Scientific accuracy by domain expert | Phase 4 |
